Part A · The ideas
IDEA 1 · THE TWO TYPES OF DATA LEAKAGE

When information from the future sneaks in

Data leakage happens when information that would not be available at real prediction time is used to build or evaluate the model. It produces scores that are too good and models that fail in production.

Target leakage

A feature is created after (or because of) the outcome. The model learns a shortcut that doesn't exist in production.

StreamBox example: retention_offer_sent is sent after the customer decides to cancel. At prediction time it is always 0.

Train-test contamination

Information from the test (validation) set leaks into the training process — usually through a preprocessing step that sees all the data at once.

Examples: scaling on all data before splitting, feature selection on all data, oversampling before CV folds.

Key signal: suspiciously good scores

A single feature with AUC 0.956 (like retention_offer_sent) should be an immediate red flag. Honest features on this dataset reach only ~0.70. Leaky features look like geniuses in the lab and idiots in production.

Check: the marketing team runs a model first thing Monday morning, before any customer has called to cancel this month. What is the value of retention_offer_sent for every row?

IDEA 2 · THRESHOLDS, TP, FP, FN, TN

The threshold decides: TP or FN?

A model outputs a probability, not a label. You pick a threshold to turn it into a prediction. Everything above → predict 1 (will churn), everything below → predict 0 (stays).

TP & TN = correct. FP & FN = mistakes.

FP vs FN: which matters?

FN (miss a churner): Customer leaves silently. Revenue lost forever.

FP (flag a loyal customer): Marketing sends an unnecessary discount email. Small cost.

For churn, FN is far more expensive → lower the threshold to catch more churners (more TP, fewer FN), accepting more FP. This depends on the business, not a universal rule.

IDEA 3 · HOW A PIPELINE SEALS LEAKAGE

The Pipeline: one object, no leaks

Without a Pipeline, you fit your imputer and scaler on all data first, then run cross-validation on the already-transformed data. The scaler has already "seen" the validation fold's values — a small but real leak for imputation/scaling, and a catastrophic one for feature selection (as in Section 4.2).

Wrong way (preprocessing outside CV)

All data → fit imputer & scaler
→
Transformed X (train+test mixed)
→
cross_val_score

❌ Validation folds saw the imputer/scaler training step. For supervised steps like SelectKBest this gives wildly fake scores (AUC 0.876 on pure noise).

Right way (Pipeline inside CV)

Raw X_train
→
Pipeline(imputer → scaler → model)
→
cross_val_score

✅ Inside each CV fold: Pipeline fits imputer+scaler only on the 4 training folds, transforms the held-out fold using those learned values. No leakage.

Full ColumnTransformer pipeline (Section 5)

numeric_transformer = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
    ("scaler",  StandardScaler())
])
categorical_transformer = Pipeline([
    ("imputer", SimpleImputer(strategy="most_frequent")),
    ("encoder", OneHotEncoder(handle_unknown="ignore"))
])
preprocessor = ColumnTransformer([
    ("num", numeric_transformer, numeric_features),   # 5 cols → 5 cols
    ("cat", categorical_transformer, categorical_features)  # 3 cols → 11 dummies
])
model = Pipeline([
    ("preprocessor", preprocessor),   # 5 + 3 raw → 16 features
    ("classifier",   LogisticRegression(max_iter=1000))
])

5 numeric + 3 categorical = 8 input columns → 16 preprocessed features (5 scaled numerics + 3+4+4=11 one-hot columns). The model object handles missing values and unseen categories automatically, in every CV fold and in production.

IDEA 4 · UNSUPERVISED VS SUPERVISED PREPROCESSING

Why feature selection leaks, but scaling barely does

Not all preprocessing steps are equal. The critical difference is whether the step looks at y (the labels).

Unsupervised (doesn't see y)

Imputation, StandardScaler, MinMaxScaler, PCA

Only uses feature distributions. Leaking these across folds on 1,600 rows shifts the score by <0.001 — noise level.

Wrong way AUC 0.7348 vs right way 0.7348 — identical.

Supervised (sees y — dangerous!)

SelectKBest, SelectFromModel, target encoding, SMOTE oversampling

Searches for features correlated with y. On 2,000 random noise features, chance guarantees some will align. Leaking this step gives AUC 0.876 on pure random data.

Right way inside Pipeline: AUC 0.425 (no better than chance).

For unsupervised steps on 1,600 rows the difference is ≈0.0001. It doesn't mean it's safe to skip — with a small dataset or outliers, the shift can be larger, and the principle of putting preprocessing inside a Pipeline is non-negotiable.

Why is 4.1 so close?

The imputer fits medians; with 1,600 rows the median barely changes if you hide 320. Same for StandardScaler: the mean and std of 1,600 vs 1,280 rows differ by <1%. Contrast with 4.2: SelectKBest searches 2,000 features for the 20 best — random chance guarantees it finds noise that correlates, and those "best features" are chosen specifically because they happened to fit the validation labels too.

All C ≥ 0.1 are within 0.001 of each other. Logistic Regression is stable and well-regularised on this problem — the data, not the C value, limits performance.

Why is grid.best_score_ still slightly optimistic?

We chose the configuration with the highest CV score across 10 configurations. That choice introduces a tiny selection bias (multiple comparisons). The best_score_ is optimistic by ≈ the noise level of one comparison. The untouched test set, evaluated only once, is the only truly unbiased number.

SECTION 7 · SPOT THE LEAKAGE SCENARIOS

Three real-world patterns to recognise at the oral exam

🏥 Scenario 1: Chest X-rays

Problem: 3,000 patients, 10,000 images, split by image (not by patient). Some images of the same patient appear in both train and test.

Type: Group / patient-level leakage.

Fix: Split by patient ID using GroupShuffleSplit or GroupKFold. All images of one patient must go entirely to train or entirely to test.

💳 Scenario 2: Fraud + oversampling

Problem: Fraud rows copied 50× on the full dataset, then 5-fold CV. Identical rows appear in both train and validation folds.

Type: Train-test contamination via supervised preprocessing.

Fix: Oversample inside the CV loop (e.g. imblearn.pipeline with SMOTE), or use class_weight="balanced" in the estimator.

🍦 Scenario 3: Ice-cream sales

Problem: Centred 7-day average uses 3 days after the prediction date. Shuffled CV mixes past and future.

Type: Temporal / lookahead bias (target leakage).

Fix: Use a lagged 7-day window (days t-7 to t-1). Evaluate with TimeSeriesSplit (no shuffling).
